# CLAUDE.md — Threaditate Storefront Theme

## What is this project?

This repo is the **Shopify storefront theme** for [Threaditate](https://threaditate.com) — a brand that turns a customer's photo into a meditative, hands-on string-art kit. This theme is what shoppers see: the marketing pages, product pages, cart, and customer account pages on the live store.

It is **the storefront only.** The string-art algorithm, the photo→pattern app, and the Supabase backend live in other repos. This theme renders the store and links out to the app; it does not run the algorithm.

- **Live store:** `threaditate.com` (primary domain). Internal addresses: `string-ring-2.myshopify.com` and `iy8zdq-5h.myshopify.com` — both point to the same store.
- **Live theme:** `Bubbly` (`#182977593639`). It is a Dawn-derived custom theme.
- ⚠️ **Pushing to `main` deploys to this live theme.** See [Git Workflow](#git-workflow) and [Deployment](#deployment). `main` is production.

### Brand context (read before writing any copy)

The brand was **rebranded from "String Ring" to "Threaditate."** Two source docs live in the repo root:

- [copy-style-guide.md](copy-style-guide.md) — the **authoritative** voice, tone, and product-language guide (Threaditate). When in doubt, this wins.
- [creative-brief.md](creative-brief.md) — a **historical** String Ring brief. Useful background, but **outdated**; where it conflicts with the style guide, the style guide wins.

Canonical product terms: **kit, loom (20-inch, 240 pins), pins, pattern, thread, piece.** Preferred verbs: **make / create / thread** (never "assemble," "build," or "string"). Some theme copy still says "String Ring" / "stringing" — that's stale and pending a copy pass; don't propagate it.

## Tech Stack

This is a standard Shopify **Online Store 2.0** theme. No framework, no build step.

- **Liquid** — Shopify's templating language (`.liquid` files in `sections/`, `snippets/`, `layout/`).
- **JSON templates + section groups** — `templates/*.json` and `sections/*-group.json` compose pages from sections. Many are **auto-generated by the Theme Editor** (see the banner at the top of those files).
- **Vanilla JS** — progressive-enhancement web components (e.g. `<superpowered-video>`). No bundler; scripts are plain files in `assets/`.
- **CSS** — hand-authored, one file per component/section in `assets/` (`component-*.css`, `section-*.css`).
- **Shopify CLI** (`shopify`) — local dev server, linting, and deploys. This is the only required tool.
- **Theme Check** — Shopify's Liquid/theme linter, run via `shopify theme check`. This is the analyzer equivalent for this repo.

## Common Commands

```bash
# Local preview with hot reload (serves THIS folder against live store data)
shopify theme dev --store string-ring-2.myshopify.com      # http://127.0.0.1:9292

# Lint the theme (Theme Check). CI fails on error-level offenses.
shopify theme check                       # full report (errors + warnings)
shopify theme check --fail-level error    # exactly what CI runs

# Inspect themes on the store
shopify theme list --store string-ring-2.myshopify.com

# Pull the LIVE theme into a SEPARATE folder (never on top of your work)
mkdir -p /tmp/live-theme
shopify theme pull --store string-ring-2.myshopify.com --live --path /tmp/live-theme

# Deploy to the live theme (normally CI does this — see Deployment)
shopify theme push --store string-ring-2.myshopify.com --live --allow-live \
  --ignore config/settings_data.json
```

First CLI run on a machine opens a browser to log into your Shopify account; the session is then cached.

## Project Structure

Shopify dictates this layout — directory names are fixed and meaningful.

```
assets/        # CSS, JS, images, fonts. Naming: component-*.css, section-*.css
config/        # settings_schema.json (theme settings UI) + settings_data.json (merchant's saved values)
layout/        # theme.liquid (global wrapper) + password.liquid
locales/       # translation strings (en.default.json + per-locale + *.schema.json)
sections/      # page-level building blocks; each has a {% schema %}. *-group.json compose section groups
snippets/      # reusable Liquid partials, included via {% render 'name' %}
templates/     # per-page templates. *.json compose sections; *.liquid are custom/legacy templates
               # templates/customers/ holds account/login/register/etc.
.github/workflows/deploy.yml   # CI: lint on PR, deploy on push to main
copy-style-guide.md            # authoritative brand voice (NOT pushed to the store)
creative-brief.md              # historical brief (NOT pushed to the store)
```

Non-theme files (the `.md` docs, `.github/`) are ignored by `shopify theme push` — only the standard theme folders are uploaded.

## Deployment

CI lives in [.github/workflows/deploy.yml](.github/workflows/deploy.yml):

- **On every PR to `main`:** runs `shopify theme check --fail-level error`. No deploy.
- **On every push to `main`:** lints, then `shopify theme push` to the **live** theme.

**Required GitHub repo secrets** (Settings → Secrets and variables → Actions):

- `SHOPIFY_FLAG_STORE` = `string-ring-2.myshopify.com`
- `SHOPIFY_CLI_THEME_TOKEN` = a password from Shopify's **Theme Access** app (`apps.shopify.com/theme-access`).

**Source-of-truth rule — important:** for any file CI pushes, **code wins.** Editing those same pages in the Shopify Theme Editor will be overwritten on the next deploy. The one exception is `config/settings_data.json`, which the workflow `--ignore`s so merchant Theme-Editor settings aren't clobbered. If you change a page's content, do it **in code**, not in the editor.

Before a large change, `shopify theme pull` the live theme into `/tmp/live-theme` and diff it against this repo, so you know exactly what a push will change.

## Git Workflow

- **Always work from a feature branch.** Never commit directly to `main`. `main` auto-deploys to the live store — treat it as production. Use descriptive names: `feat/faq-rewrite`, `fix/text-image-dark-tag`, `chore/deploy-workflow`.
- **Commit often.** Small, frequent commits, each a logical unit of work. Don't batch unrelated changes.
- **Conventional commit messages.** Use prefixes:
  - `feat:` — new section, snippet, page, or capability
  - `fix:` — bug fix (broken Liquid, layout, link, accessibility)
  - `refactor:` — restructuring with no visible change
  - `content:` / `copy:` — storefront copy changes (or `docs:` if you prefer)
  - `chore:` — CI, tooling, dependency/asset housekeeping
  - `perf:` — performance (image sizing, lazy-loading, reducing render-blocking assets)
  - `style:` — formatting only
- **Submit PRs back to `main` using `gh pr create`.** Clear titles using the same prefixes. The body must include a **summary** and a **verification plan** (see [Quality gates](#quality-gates--verification)) — for a theme that means how you previewed it and the Theme Check result, not unit tests.
- **The user reviews and merges all PRs.** Do not merge autonomously. Merging to `main` ships to the live store.
- **NEVER add `Co-Authored-By` or "Generated with Claude Code"** to commits or PRs.

## Quality gates & verification

This is a Liquid theme — there is **no unit-test framework here**, so don't pretend there is or fabricate one. Quality is enforced by linting plus disciplined manual verification. Both are required before a PR is mergeable.

- **`shopify theme check --fail-level error` must pass.** CI enforces it. Fix real errors (`LiquidHTMLSyntaxError`, `MissingAsset`, broken `{% render %}`); don't suppress them. Pre-existing warnings are tolerated but don't add new ones.
- **Preview every change with `shopify theme dev` before pushing.** Look at it in the browser. A change you haven't seen rendered is not done.
- **Check every template that uses the section/snippet you touched.** A shared snippet (e.g. `card-product`, `button`) can appear on many pages — verify them, not just the one you were working on.
- **Responsive + accessibility.** Check mobile and desktop widths. Keep alt text, headings, and focus order intact. Don't regress contrast or keyboard navigation.
- **Don't break the Theme Editor.** Section `{% schema %}` settings must stay valid JSON with stable `id`s — renaming or removing a setting `id` orphans a merchant's saved value.

### Not acceptable excuses

- **"It's just a copy change."** Wrong domain still ships to customers. Run it past [copy-style-guide.md](copy-style-guide.md) and preview it.
- **"It's a tiny Liquid tweak."** Tiny tweaks break rendering. Preview it.
- **"Theme Check passed, so it's fine."** Theme Check catches syntax, not whether the page looks right or the copy is on-brand. Look at it.

## Code Standards

### Clean Liquid & assets

- **DRY:** extract repeated markup into a snippet and `{% render %}` it. If you're copy-pasting Liquid, make a snippet.
- **Single responsibility:** a section does one job; a snippet renders one thing. If a section's purpose needs an "and," consider splitting it.
- **Small, readable templates:** keep section markup scannable. Push complexity into snippets and well-named `{% liquid %}` blocks rather than deeply nested inline conditionals.
- **No dead code:** remove orphaned snippets, unused assets, and commented-out blocks. Theme Check flags `OrphanedSnippet` and unused assets — act on it.
- **Match the surrounding style.** This theme has established naming (`component-*.css`, `section-*.css`, BEM-ish class names like `text-image-dark__btn`) and schema conventions. New code should be indistinguishable from existing code.
- **Naming:** files `kebab-case.liquid`; CSS classes follow the existing block/element pattern; section setting `id`s are stable, descriptive `snake_case`.

### Liquid discipline

- **Escape output that could contain HTML you don't control.** Prefer the right filter; use `| escape` for plain-text settings rendered into markup. Only emit raw HTML (`| metafield_tag`, rich-text settings) when that's the intent.
- **Use translation keys** (`{{ 'foo.bar' | t }}`) for user-facing strings where the theme already does — keep `locales/` in sync. Hard-coded English in a section that otherwise uses `t:` is a regression.
- **Guard for blank.** Settings and metafields can be empty. Wrap optional content in `{% if x != blank %}`.
- **Lazy-load and size images.** Use the theme's image snippets/`image_url` with width/height; don't drop full-resolution `<img>` tags into the page.

## Security

- **Security is a priority, not an afterthought.**
- **Never commit secrets, tokens, or credentials.** The Theme Access token and store address live in **GitHub Secrets only**, never in the repo. There is no `.env` checked in.
- **`config/settings_data.json` can contain app/API keys** entered by merchants. Don't paste it into issues/PRs, and remember CI `--ignore`s it.
- **Treat customer-controllable data as untrusted.** Escape anything derived from URL params, customer input, product reviews, or metafields before rendering into HTML. Never build a `<script>` body or inline handler from user-controlled strings.
- **Be cautious adding third-party `<script>` tags.** Each one is an attack surface and a performance cost. Prefer Shopify's native features; if you must add a script, scope it and load it `defer`/`async`.
- **Respect Shopify's auth & checkout.** Authorization is Shopify's job (customer accounts, checkout). Don't reimplement it in Liquid or gate content with client-side JS as if it were security.
- **Deep links / redirects:** sanitize any `?return_url=`-style params; never redirect to an unvalidated user-supplied URL.

## Things to know before making changes

- **`main` is live.** A merged PR (or any push to `main`) deploys to the `Bubbly` theme on the production store. There is no staging theme wired into CI yet — if you want one, push to a specific unpublished theme by ID (`shopify theme list` for IDs) instead of `--live`.
- **JSON templates are auto-generated.** Files like [templates/page.faq.json](templates/page.faq.json) carry an "auto-generated" banner because the Theme Editor can rewrite them. Editing them in code is fine **as long as the team treats code as the source of truth** for those pages and doesn't also edit them in the editor (the next deploy would overwrite editor changes).
- **`settings_data.json` drifts.** The repo's copy lags what merchants set in the editor. CI ignores it on purpose. Don't "fix" the drift by force-pushing it unless you mean to reset merchant settings.
- **Navigation menus and Pages are NOT in this repo.** They live in the Shopify admin (Online Store → Navigation / Pages). A nav link pointing at the wrong page, or a missing page behind a `shopify://pages/<handle>` link, is fixed in admin, not here.
- **`assets/section-product-hero.css` is an intentional empty placeholder** — the original was lost (it's missing from live too). Restore real styles there if recovered; don't delete the file (it prevents a `MissingAsset` error and a 404).
- **Stale brand copy exists.** Several sections still use String Ring language and the old product. Use [copy-style-guide.md](copy-style-guide.md) terms when you touch them, and flag larger copy cleanups rather than silently rewriting unrelated sections.
